## 个人 AI Vibe Coding 系统架构方案（v0.1 → v0.2）

- 产出：`src/engineering-system/ARCHITECTURE.md`（设计方案，未落地运行文件）
- 定位：个人产品快跑型 + Web 全栈（Next.js/TS），区别于团队级 `tools/ai-copilot-template`

### v0.8 网络调研后红线定稿（33 行）

- 用户要求「搜索网络资料补充更多红线」。调研来源：Anthropic Claude Code 实践指南、GitHub 2500+ AGENTS.md 分析、Reward-Hack-Bench / Hack-Verifiable Environments、vibe-coding-wiki、dev.to 关于 agent 删测试的案例
- **反直觉结论**：业界一致是「少而硬」不是「多而全」。alphalab 实测 26 行与 433 行版本都是 4/4 通过；Anthropic 判据「删掉这行模型会不会犯错，不会就删」
- 终极红线定为 6 条，新增两条：
  - **不为通过检查而改检查**（reward hacking）：删测试 / .skip / 弱化断言 / 把期望值改成实际值 / 改 OpenAPI 让契约测试过 / catch 吞错。可检查信号 = diff 是否碰测试、配置、锁文件
  - **不把秘密带出去**：2500+ 仓库中出现频率第一的约束
- 其余扩展：不扩范围补「加依赖、换包管理器」；不破坏已有工作补「不自动 commit/push」
- 淘汰 8 条候选（歧义先问、日志当事实、先读代码、写测试、生成文件、push main、生产只读、auth/billing 前确认），理由写入 docs §6.2
- **关键判据（docs §6.3）**：Anthropic 明确区分确定性/非确定性指令——反复强调仍不遵守的条目应进 hook / deny rule / CI，不是继续加粗。6 条里「不泄密」「不自动提交」两条提示词管不住，需外部化
- 结论：撞两次以上的事故 → 配 hook 或 CI，不加第七条红线
- 用户追问「不过度抽象、不防御编程」为何缺席。判断：不进红线（红线 = 不能有例外 + 违反即欺骗；这两条是有例外的质量判断，写成红线会变成"一律不许抽象/判空"）

  - 边界：`catch { }` 吞错归红线 2（让失败看起来像成功），不算代码风格
