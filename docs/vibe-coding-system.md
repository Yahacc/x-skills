# 个人 AI Vibe Coding 系统 · 设计说明 v0.5

> 阅读对象：只有你。本文档是设计说明，不会被任何 agent 加载。
> 一句话：把「个人做 Web 全栈小产品」这件事里，模型记不住、不敢决定、也不负责的部分，做成可复用的资产。

## 1. 这个仓库是什么，不是什么

**是**：个人 skill / prompt / 模板的统一管理处。内容按「形态」分类，每类有明确的消费方式——被安装、被复制、被引用、被阅读。

**不是**：运行环境。agent 不会在这个仓库里工作，所以这里不存在运行时上下文。

**`src/` 不是源码。** 它装的是**成套的系统包**：一组互相依赖、必须一起装的产物（全局规则 + 项目模板 + 技能）。和散装资产的区别是「能不能单独用」——`prompts/riper5/` 可以单独装，`src/` 里的几份拆开装就不成立。

三个直接推论：

- 根目录的 `AGENTS.md` 是**仓库维护约定**（不自动暂存提交、不删 `.agents/`、不改 MCP env），和「目标项目的 agent 规则」是两件完全不同的事，不要往上加工程方法论。
- `.agents/` 这类运行时目录只应出现在**模板**内部，作为复制到目标项目后的结果，不出现在仓库根。
- 判断一个文件该放哪里，只问一句：**谁读它、怎么读？** 答案决定形态，形态决定位置。

## 2. 产物形态与存放位置

| 形态 | 谁消费、怎么消费 | 位置 | 本仓库现状 |
| --- | --- | --- | --- |
| **System** | 成套安装：全局配置 + 项目模板 + 技能，缺一份不成立 | `src/` | 本系统 ✅（3 份 + README） |
| **Skill** | agent 按需加载，带触发条件 | `skills/<name>/SKILL.md` | 6 个散装技能 |
| **Prompt** | 人贴进某个工具的 system prompt | `prompts/*.md` | `ai-engineering-agent.md`、`riper5/` |
| **Template** | 复制到目标项目根目录，成为那边的事实 | `tools/<name>/` | `ai-copilot-template/`（团队用） |
| **Doc** | 只有人读 | `docs/*.md` | 本文件 |

本系统的技能放在 `src/skills/` 而不是 `skills/`，因为它是**包的一部分**：改全局规则时，切片技能的判据要跟着改，两者必须一起版本化。散装技能没有这个约束。

四类的边界要守住：

- **Skill 里不写项目事实**，只写「什么时候用、按什么判、什么情况算反例」。
- **Prompt 里不写教程**，只写约束、判据和事实骨架；模型本来就会做的事不写。
- **Template 里不放方法论解释**，只放待填的占位符和一句指路。
- **Doc 里不承诺可执行**，不写成「照做即可」的操作手册。

## 3. 判断前提：模型内置了什么，没内置什么

整套设计的地基。判断错了，后面的预算分配全错。

| 模型已内置（不用教） | 模型内置不了（只有系统能给） |
| --- | --- |
| 流程知识：该澄清、该拆、该先写测试 | 跨会话状态：新会话零记忆，不记得上周的决定 |
| 动作能力：读仓库、改代码、跑命令、自查 | 不可逆边界：不知道哪张表不能删、哪个字段有旧版本在读 |
| 大部分工程规范：命名、目录、测试习惯 | 独立证据：同一上下文里自证，需求错了会自洽地证明自己对 |
| 自我修正：报错后重试、构建失败后改 | 后果承担：错了不由它负责，天然倾向「看起来完成」 |

两条反直觉，决定系统长什么样：

**① 能力越强，失败越安静。** 弱模型编译不过，你一分钟发现；强模型编译过、测试绿、需求理解偏，上线才发现。所以「模型变强了，流程可以省」在失败**可检测性**上正好是反的。

**② 规范会贬值，事实不会。** 今天写进 skill 的「先写测试再做实现」，三年后是模型默认行为；但「这个项目用 pnpm + App Router、`/api/legacy` 不能动、数量按累计值展示不受时间过滤影响」——模型永远猜不到。

因此系统定位是：**给状态、划边界、要证据**。不是教方法。

> 判别标准（用于删规则）：一条规则写进去，如果删掉之后模型仍然会那样做，它就不该存在；如果删掉之后模型开始乱来，它才值得留下。

## 4. 三角分工

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 模型 | 理解需求、写实现、跑验证、提方案 | 记忆、授权、承担后果 |
| 资产（本仓库产出） | 保存事实、约束行为、定义完成、留存决策 | 教模型已经会的东西 |
| 你 | 定「做什么/不做什么」、划不可逆边界、判断证据够不够 | 逐行审查、复述上下文、当人肉 linter |

你的价值不在「监督规范」，在**提供模型拿不到的信息**和**做它做不了的取舍**。

## 5. 落地后的形态：两层常驻 + 一层按需

```
全局常驻    src/global-agents.md → 由你装到用户级配置（33 行）
             ↓ 每个项目都生效；只写行为，不写任何项目事实
项目事实    项目根 AGENTS.md（59 行骨架）
             ↓ 只在需要「怎么做」时按需加载
能力层      src/skills/*（SKILL.md ≤40 行：触发条件或路由 + 判据 + 反例）
```

启动上下文 = 33 + 59 ≈ 92 行，150 的预算里还剩三分之一。

**没有 `index.md` 路由层。** 路由的价值只在「内容多到不能全读」时成立。项目事实压到单文件后，直接全读比查表更快、更不易错；多一层就多一个会失真的地方，而失真的路由不会报错，只会让 AI 少读一个本该读的文件。内容涨到一页读不完时再加，不提前建。

**红线只写一次。** 红线在全局，项目层不重复。项目层要更强的约束时写「一律先出计划 + 切片卡」，而不是抄一遍红线。

### 预算（硬上限）

| 预算项 | 上限 | 超了怎么办 |
| --- | --- | --- |
| 启动上下文 | ≤150 行（全局 + 项目 AGENTS） | 说明职责重叠，合并或删 |
| **全局规则** | **≤40 行** | 它对每个项目生效，加一条必须删一条 |
| 单个 SKILL.md | ≤40 行 | 超了说明掺了教程、背景或项目事实 |
| 单个参考文件 | 不限，但一份只写一件事 | 出现「另外」或「顺便」，拆开 |
| **事实类**（项目 AGENTS 全篇） | 不限，但不写无复用价值的内容 | 换个项目还成立 → 那是方法，不该写这 |
| 单个切片 | 装得进一个新鲜上下文窗口 | 先切分，不许一次梭哈 |

当前账：启动 33 + 59 = 92（余 58）；全局 33 / 40；三个 skill 的 SKILL.md 分别 40 · 33 · 39，参考文件另计。

**为什么 skill 不受总量约束。** 上一版写的是「规则类总量 ≤120 行」，那是个错误：skill 按需加载，根本不进启动上下文，把它和常驻规则算进同一个池子，等于让「加载时才付费」的东西挤占「每次都付费」的额度。结果是加一个 skill 就要从全局删一条红线——而红线比任何 skill 都重要。

正确的分账是三层三本账：**启动上下文（每次都付）/ 全局规则（每个项目都付）/ skill（用到才付）**。前两个卡死，第三个只要单个装得进上下文就行。

规则和事实分账是另一条核心设计。**规则是易耗品，事实是资产**；放进同一个上限，扩规则时就会挤掉事实。

## 6. 全局那 33 行

成品在 `src/global-agents.md`。四段，每段防的东西不同：

| 段 | 防御对象 |
| --- | --- |
| 红线 6 条 | 伪造完成、改检查让自己通过、夹带扩范围、覆盖已有工作、带出秘密、替用户拍低可逆决策 |
| 开工判断 | 模型按「表述规模」判断轻重——短句里藏着跨端改动时它会一把梭 |
| 收尾（只声明要做 review） | 模型一次笼统自查：「都改好了」代替真的回看；顺带查「没有触发条件的代码」 |
| 项目事实指针 | 模型凭印象猜栈和命令，而不是去读 |

### 6.1 六条红线的来源

底子取自 `prompts/ai-engineering-agent.md` §3.2（六条），再对照三份外部资料校正：Anthropic 的 Claude Code 实践指南、GitHub 对 2500+ 个 AGENTS.md 的分析、以及奖励劫持（reward hacking）相关的研究记录。

| 红线 | 从哪来 |
| --- | --- |
| 不编造、不伪造完成 | 原 §3.2 第 1 条 + Anthropic「不要断言成功，要给证据」 |
| 不为通过检查而改检查 | **新增**。奖励劫持研究里最稳定的失败模式：删测试、`.skip`、弱化断言、把期望值改成实际值、改 OpenAPI 让契约测试通过、`catch { }` 吞错误 |
| 不静默扩大范围 | 原第 3 条，补上「加依赖、换包管理器」——资料里这一条出现频率仅次于密钥 |
| 不破坏已有工作 | 原第 5 条，补上「不自动 commit / push」 |
| 不把秘密带出去 | **新增**。2500+ 仓库里出现最多的单条约束，没有之一 |
| 不替用户做低可逆决策 | 原第 6 条，收窄成「决策」而非「动作」，避开与开工判断重复 |

新增的第二条之所以单列、不并入第一条，是因为机制不同：第一条管**说假话**，这一条管**把标准改成假话成立**。后者更隐蔽——测试全绿、构建通过、lint 干净，唯一的异常是 diff 里动了测试文件。它也因此有一个极便宜的可检查信号：**看 diff 有没有碰测试、配置和锁文件**。

### 6.2 加不进去的，和为什么

搜索到的候选远多于六条。下面这些被淘汰，理由分三类：

| 候选 | 淘汰理由 |
| --- | --- |
| 不确定就停下来问 | 已被开工判断第一个开关覆盖，写两处只有一处会更新 |
| 不把日志当天然事实 | 只在排障时发生，属 `debug` 的触发面 |
| 先读代码再改 | 模型默认会读；写了也不改变行为 |
| 保持简洁 / 写测试 / 优先可读 | 同上，全是模型默认行为 |
| 不改生成文件、不动 vendor | 是项目事实（哪些目录是生成的），该进项目 `AGENTS.md` 的禁改区 |
| 不直接 push main、PR 要带证据 | 团队流程，个人项目没有这条链路 |
| 数据库与生产系统只读 | 同上，属项目状态与授权范围 |
| 改 auth / billing / migration 前确认 | 是「跨模块 + 不可逆」的具体化，已被开关和判据覆盖 |
| 不过度抽象、不防御性编程 | **没进红线，但没丢**——见下 |

**「不过度抽象」「不防御性编程」为什么不进红线。** 两条都真实、都高频，但性质与红线不同：红线是「不能有例外、违反即欺骗」的硬边界（假绿、泄露、覆盖别人的工作）；这两条是**有例外的质量判断**——有些地方就该抽象，有些判空确实必要。写进红线会变成「一律不许抽象、一律不许判空」，那比不写更糟。

它们的位置是两处：

- **可判定的一句进收尾**：review 时看「有没有没有触发条件的代码」——说不出哪种真实输入能触发的判空、兜底、catch、默认值、抽象层。这是唯一的硬判据，因为它能落到具体代码上核。
- **具体判断进 skill**：`api.md` 有「边界之后还在反复判空，说明边界没做干净，而不是更安全」，以及 `catch (e) { console.log(e) }` 后继续跑这个识别标志；`component.md` 有「抽象只保留能解释重要业务约束的，固定 columns 和字段映射直接写」。

放收尾而不是开工，是因为它不决定「要不要做」，只决定「做完要不要收拾」。放进开工判断会让每次小改动都先自证一番，而这类问题恰恰是写出来才看得见的。

顺带一条界线：「`catch { }` 吞掉错误」不属于这里——它归红线第 2 条。吞错不是代码风格问题，是**让失败看起来像成功**，和删测试同一类。

### 6.3 一个比「再加一条」更重要的判据

Anthropic 的实践指南里有一句话，值得当作加红线的闸门：

> 如果你反复给某一行加强调、模型还是不照做，说明这一行该放进 hook，而不是继续加粗。

它把指令分成两类：**模型读到后会自己决定的**（提示词、skill），和**执行层强制执行的**（hook、deny rule、CI、分支保护）。绝大多数规则属于前者，该让模型自己判断；少数「不能有例外」的属于后者，写在提示词里只能做到「大概率不发生」。

按这个判据，六条里至少两条是**提示词管不住的**：

- **不把秘密带出去**：真要不发生，靠 `.gitignore` + pre-commit 扫描 + 密钥不进仓库，不靠一句「不许」。
- **不自动 commit / push**：真要拦住，靠工具层的权限配置或 hook，不靠 AGENTS.md。

写进全局仍然有价值——它让模型知道边界在哪，很多情况下它自己会停。但**不要把「写了」当成「有了」**。这条区分也解释了为什么不该继续加红线：提示词里每多一条，就多一条「写了但不生效」的错觉，最后你没法判断哪条在起作用。

如果一个高频事故已经撞了两次以上，正确的动作不是回来加第七条红线，而是给它配一个 hook 或一条 CI 检查。

### 6.4 其余三段的理由

**「任务 → 技能」已删除，连同整段索引。** 两个理由：skill 靠自己的 `description` 触发，索引本来就不承担触发；更关键的是，在全局写死「这类任务用那个 skill」，等于我替模型决定了这件事该走哪条路——而流程判断本来就该交给它按当下情况做。写索引是用自主权换查表。

**判据必须可查，不能凭感觉。** 「跨模块」「改对外行为」各给了一条可对照的定义（跨顶层目录 / 跨层调用 / 跨包；HTTP 契约 / props / 导出签名 / DB 字段语义 / 公共 token），因为它们要同时用于开工前和收尾检查两个时刻，模糊一次就有两处一起失准。

**不写进全局的**：任何具体路径、任何栈和命令、任何「保持简洁」「先理解需求」类的话。前者是项目事实，后者模型默认就会做。

## 7. 项目那 59 行

成品骨架在 `src/project-agents.md`，字段是硬清单：

`一句话 / 栈 / 命令 / 证据 / 目录地图 / 禁改区 / 约定 / 状态（含更强约束声明）/ 坑`

**「证据」段是验证矩阵的载体。** 矩阵本身是方法，但「能跑什么命令、能截什么图、线上有哪几条冒烟」取决于项目里有什么工具，所以它必须和命令清单放在一起，而不是躺在设计文档里。同理，「接缝越靠上越好」这句话写在这里，才会在每次决定怎么证明时被读到。

**这份文件唯一的读者是 AI，它只想知道「这里和别处哪里不一样」。** 所以项目历史、产品愿景、迭代计划都不进来——那些进你的笔记。

三条写入纪律：

1. **AI 能查到的，不要问人。** 目录结构、依赖版本让它自己查仓库；写进去的应该是它查不到或查起来很贵的东西。
2. **人才能定的，不要让 AI 默认。** 「要不要兼容旧版本」「这个功能先不做」「哪个接口线上在跑」有后果，必须由你写下。
3. **只收长期有效的。** 临时字段、一次性排期写进去，会把事实文件变成垃圾场，然后 AI 开始跳过它。

**没有单独的 `notes.md`。** 决策和坑都进「坑」段，每条一行「现象 → 结论」。需要写长说明的决策，写进项目仓库自己的设计文档，这里只留指针——否则同一个事实有两个版本，先过期的那份没人删。

## 8. 能力层：skill 给判断标准，不给流程

三个 skill，都在 `src/skills/`。

| 技能 | 触发 | 核心动作 | 结构 |
| --- | --- | --- | --- |
| `slice-planning` | 需求说不清、跨模块、改对外行为 | 切成穿透每层的垂直切片 | 单文件 40 行 |
| `frontend-feature` | 页面、组件、样式、接口、数据校验 | 先判断碰哪层，再读那层的判据 | 路由 33 行 + 三份参考 34/32/41 |
| `debug` | 报错、白屏、构建失败 | 先有能红的信号，再谈原因 | 单文件 39 行 |

### 为什么前端的三块合成一个、另外两个不并

`web-ui` 和 `api-contract` 原来各是一个 skill，现在合成 `frontend-feature`，`SKILL.md` 只做路由。

**理由是触发竞争，不是省 token。** 「加一个带接口的页面」会同时命中两个 description，模型要么重复加载、要么只挑一个——挑错那个就丢掉一半判据。合并后判断发生在 skill 内部，一次触发，由路由表决定读哪几份。

`slice-planning` 和 `debug` 不并进来，因为它们不是前端专属：前者是任务形状，后者是确认原因的方法，后端、构建、部署一样用。捆进「前端」会让它们在后端项目里失效。

**代价要说清**：单层任务现在多读 33 行路由（原来直接读 40 行），跨两层的任务多读 21 行。换来的是一个入口、一次触发。这个交换在触发精度上是赚的，在 token 上略亏——所以 `SKILL.md` 里必须写死一句「不读参考就动手，等于没用这个 skill」，否则路由会空转。

### 写法：给自主权，不给流程

参照 `mattpocock/skills` 的取向——它的 `implement` 只有 15 行，`tdd` 是一份「好测试长什么样 + 反模式的识别标志」的参考，而不是 1-2-3 步骤。理由是**写死的步骤会挡住模型对具体情况的判断，判断标准不会**。

具体三条：

1. **一个 skill 只有一个核心动作**，用一句能记住的话说清（`debug` 就是「先有能红的信号」）。其余内容都是围绕它的判据、完成标准、反例。
2. **给选项清单，标注各自的适用条件**，不规定必须按顺序走。`debug` 列了五种建信号的方式，模型按手头条件挑。
3. **反例写成「识别标志」**，写成「看到 X 就说明 Y」。比禁令有效：禁令要靠人记住，识别标志只要看一眼代码就能对上。

**能自主的前提是判据可查。** 「状态写全」「边界只校验一次」都能落到具体代码上检查；「代码要优雅」不能，所以不写。

### 不写的两类

- **教程**：解释「为什么垂直切片更好」的开场白。模型知道，写进去只占上下文。
- **项目事实**：目录结构、颜色值、命令。这些在项目 `AGENTS.md`，写进 skill 就会过期。

`component-engineering`（原独立技能：45 行路由 + 123 行场景）已并入 `references/component.md`（41 行）。它答「组件怎么设计」，和 ui、api 答的不是同一个问题，但它们是**同一个任务的相邻步骤**：设计边界 → 写界面 → 接接口。分开时会出现第四份并行的方法论，模型得自己判断先用哪个。

并入时没有保留「设计 / 新增 / 改造 / 简化 / 评审」五个场景文件的分法。读完那五份会发现：方法完全同一套（定位归属 → 还原现有行为 → 分清所有者 → 最小改动 → 针对性验证），差别只在输出物——**改代码、只出方案、只评审**。按起点（新增还是编辑）分场景，等于把同一条方法抄五遍，改一处要同步五处。

所以单文件按「输出物」组织：一条主方法 + 一张三行表，说明「要改代码 / 只要方案 / 只要评审」各做什么、各不做什么。评审那一行的重点是后半句——不改文件、不把风格偏好写成缺陷，这是三个输出里最容易越界的一个。

## 9. 契约层：接缝、矩阵、双轴自检

这一层**没有独立文件**。内容分两处落地：接缝规则和矩阵写进项目 `AGENTS.md` 的「证据」段（因为「能跑什么命令、能截什么图」取决于项目有什么工具）；双轴两问和完成定义靠全局红线 + 收尾动作执行。设计说明留在这里，是因为它是改那张表的依据。

### 9.1 先定接缝，再定证据

证据落在**哪个观察点**，是设计阶段的事，不能在写的时候临场发明。三条规则：

- 优先用**已有**接缝，不为验证新造入口
- 接缝**越高越好**：接口响应 > 数据层 > 页面渲染。页面测试 PASS 而接口返回了不该返回的数据，是常见事故
- 理想数量是**1 个**。需要 3 个以上接缝才能证明一个切片，说明切片没切好

### 9.2 验证矩阵

| 改动类型 | 最小验证 | 证据形态 | 证明什么 |
| --- | --- | --- | --- |
| 纯样式 / 静态页面 | dev 起服务 + 目标页截图 | 截图路径 + 一句话看什么 | 观感 |
| 组件交互逻辑 | 单测或手动路径复现 | 测试输出 / 操作步骤 | 行为 |
| 路由 / 接口 | 实际请求一次：状态码 + 返回形状 + **不该出现的字段是否出现** | curl 输出（截关键行） | 契约 |
| 数据层 / schema | 迁移 dry-run + 一次写入再读回 | 命令输出 | 一致性 |
| 依赖 / 构建 | `pnpm build` 或 `next build` | 构建结果摘要（含警告） | 可构建 |
| 上线 | 部署 + 3 条冒烟（首页 / 主流程 / 关键接口） | 线上 URL + 状态 | 可用 |

**证据必须新鲜**：本次执行产生、可重复。上次的截图不算证据。

**验证节奏**：typecheck 频繁跑、单个测试文件频繁跑、全量测试只在收尾跑一次。不要每个小改动都 `build`。

### 9.3 检查（review）：时机与强度

检查不从属于分档，独立成节。**时机由计划结构决定**：

| 时机 | 强度 | 查什么 |
| --- | --- | --- |
| 每个计划节点 | 轻 | 该节点产出是否成立（看见结果）+ 是否偏离计划 |
| 任务完成 | 重 | 双轴两问（见下）+ 换新鲜上下文 |
| 前提被推翻 | 立即 | 不是重看代码，是重看计划：目标或边界变了，先停下来 |

没有计划的活只有一个节点：完成时。所以**完成时那次重查不能省**——它是不做计划时唯一的检查点，这也是它必须是最重一档的原因。

**双轴两问，分开问，不合并不加权：**

1. **Standards**：这改动合项目已有规范吗？（命名、目录、依赖方向、样式 token）
2. **Spec**：这是当初要的东西吗？逐条回看切片卡的「目标」和「不做」

为什么必须分开：合并之后，「代码写得好」会和「需求做得对」混成一项，一个 FAIL 会被一堆 PASS 平均掉。真实事故长这样——页面没渲染隐藏数据（PASS）、代码结构合规（PASS）、接口响应仍带着隐藏数据（FAIL），而 FAIL 才该阻塞发布。

**频次上避开两个坑**：不要边写边查（查的是半成品，还打断节奏）；不要全做完再查（错误堆积，上下文已被自己污染）。计划节点是唯一合理的检查点。

**节点轻查、收尾重查**：一个八步的计划不需要八次完整复查，否则你会放弃复查。

**换新鲜上下文**是自证闭环唯一的解法。同一主体理解需求、写代码、补测试、宣布通过，需求错的时候，代码和测试会一起证明它对。换个主体问一遍，比多跑五条测试有效。

个人场景不出报告、不做严重度分级，两问答完写进交付说明一行。

### 9.4 完成定义

**目标达成 + 范围未扩 + 每个计划节点有新鲜证据 + 完成时双轴两问都过 + 留下回滚点。**

## 10. 环：开工判断 + Vibe Loop 五步

**0. 开工判断（三个开关）** — 不看 diff 大小、文件数、行数。三个开关独立判断，可同时打开：

| 开关 | 触发条件 | 动作 |
| --- | --- | --- |
| 问清楚 | 说不清「做完是什么样」 | 先问，不动手 |
| 计划 + 拆切片 | 跨模块或跨层；改对外行为（HTTP 契约 / 组件 props / 导出签名 / DB 字段语义 / 公共 token） | 出计划 + 拆成可验证片段 + 5 行卡 |
| 回滚点 | 不可逆（删数据、迁移、线上配置、密钥） | 先给影响范围与还原方式 |

三个都不触发 = 直接做，做完给一句话结果 + 一个能看见的效果。

用开关而不是档位，是因为**判错只会漏一项，不会整体降档**——而漏掉的那项，事后是能看出来的。

**判据必须可查，不能凭感觉。** 「跨模块」和「改对外行为」各定三条，判断时对照，不靠印象：

- **跨模块** = 跨顶层目录 ／ 跨层调用（UI 直接碰数据层、组件直接发请求） ／ 跨包或仓库边界
- **改对外行为** = HTTP 契约（路径、入参、返回形状） ／ 组件 props ／ 导出签名 ／ DB 字段语义 ／ 公共 token

三条都不命中才算局部。**「一处改动」不等于「局部改动」**：diff 十行但改了 props 语义，比 diff 三百行的样式重构危险得多——前者下游有调用方，后者只有浏览器。

这也解释了为什么不能再用「中等规模以上先计划」：那是按**体量**分的，量小但改对外行为的会漏掉，量大的纯样式重构会被拦。两套判据并存时，先触发的那套决定结果，于是误判无法被纠正。

任何一档都**先读项目事实**。那只是几十行，成本近乎为零，而它是唯一防止凭印象猜的手段，省掉它等于在最快的路径上关掉了防错机制。

**1. 切片** — 一句话需求 → 一张切片卡。四条规则：

- 每个切片**窄但穿透每一层**（数据 / 接口 / UI / 测试），不做单层横切
- 切片做完必须**能演示或能验证**；说不清「做完能看什么」就是没切到位
- 一个切片**装得进一个新鲜上下文窗口**
- 必要的**预重构先做**（比如先把逻辑从特殊分支里移出来），否则切片会卡在半路

卡片模板（5 行，可省掉大半返工）：

```
目标：<做完之后我能看到什么>
范围：<只改这几个文件>
不做：<明确排除的相邻需求>
证据：<接缝 + 怎么证明：截图 / curl / 测试输出>
回滚：<commit 点 或 还原方式>
```

依赖没理清就不要并行。「不做」这一行是防扩范围最有效的一句。

**2. 定证据** — 按 9.1 选接缝，按 9.2 选那一行。顺序反了就会出现「写完了不知道怎么证明」。

**3. 实现** — ≤3 文件，先跑通再收拾；命名和局部写法允许先丑。失败反复出现且指向方案本身 → 退回切片或方案，别硬修。

**4. 验证** — 跑矩阵对应行，拿到本轮输出。只改完没跑，等于没做完。

**5. 收口** — 三件事：

- 一个可回滚 commit（一个切片 = 一个可回滚单元）
- 有决策或踩坑才写项目 `AGENTS.md` 的「坑」段，一行一条
- **跨会话的活留 5 行交接，引用路径不复制内容**：

  ```
  目标：<这个切片要达成什么>
  已完成：<做到哪>
  依据：<Spec / 决策 / commit 路径>（引用，不复制）
  剩余风险：<没验证到的部分>
  下一步：<接着干什么>
  ```

  交接是临时的，存临时文件或会话末尾，不塞进工作区变成第二份会过期的事实源。

### 会话治理

单会话超过约 30 轮、或已跨过两个功能 → 开新会话，用 `profile` + 当前切片卡重建上下文。

依据是长上下文的性能退化（Context Rot）：token 装得下，不等于模型会始终同等重视。**切片的正确尺寸标准不是「几个文件」，而是「能不能装进一个新鲜上下文窗口」。**

卡住两次仍无进展 → 停下，把现象和已排除项写进项目 `AGENTS.md` 的「坑」段，换会话带证据再问。

## 11. 反模式清单

- 一上来建「通用组件库 / 工具函数」（没有真实重复就内联）
- 为 20 行能解决的问题引入依赖
- 按技术层横切任务（改协议 + 改接口 + 改页面），最后一项完成前什么都验不了
- 页面测试 PASS 就当功能对了 → 接口是否返回了不该返回的字段
- 假验证：只跑 lint 就说完成；拿上次输出当证据；「理论上可以」
- 检查放在「全做完」之后：错误堆积，且上下文已被自己污染
- 边写边查：查的是半成品，还打断节奏
- 用档位标签代替判断：一旦贴上「轻」，检查也跟着被省掉
- 无声扩范围：顺手重构别的模块、顺手升级依赖
- **把运行时文件放进资产库**：在 x-skills 根放 `.agents/`，等一个永远不来的 agent
- 把规则当资产写：把「写测试」「保持简洁」写进 AGENTS
- 用 skill 讲原理：一段解释「为什么垂直切片更好」的开场白
- 空壳占位：先建一堆用不上的目录表达「体系完整」

**资产库这边到此为止。** 剩下的都是**在真实项目里验证**，不是在仓库里继续写：

1. **不自动装**。`src/` 是源文件，装不装、装到哪由你决定。本仓库不写入任何工具配置——一旦写了，源文件和生效副本就会分叉。
2. **装完必验**：新开会话问「这个项目哪三类改动要先确认」，答不上来说明没生效。
3. **建第一个真实项目的事实**：不能用占位符试，占位符会写出一个「看起来很完整但全是假的」文件，比没有更危险。
4. **跑一轮**：选一个跨模块的改动，看切片卡填不填得出来。填不出来是卡片字段的问题，回来改这里。
5. **看路由有没有空转**：如果它读了 `frontend-feature/SKILL.md` 就直接写代码、没打开 references，说明那句「不读参考就动手等于没用」不够硬，改措辞或把它挪到第一行。

**不做的**：`tools/vibe-coding-template/`。`src/project-agents.md` 直接复制就是模板，再包一层目录只是给「体系完整」看的。

**长期**：每两周看一次行数，全局超 40 行就删规则；每月一次「删规则复盘」，目标是「删掉后模型行为不变」的条目归零。

## 14. 验收标准

1. 新会话 30 秒内能答出：什么栈、跑什么命令、哪些不能动
2. 任意一个功能切片，15 分钟内走完一轮（开工判断 + 五步）并留下**本轮**证据
3. 全局 ≤40 行、启动上下文 ≤150 行；每次加规则都删掉了一条等价的
4. 项目 `AGENTS.md` 的「禁改区」和「坑」各有 ≥3 条真实条目
5. 两周后回看「坑」段，能看懂当时为什么那么做
6. 本仓库根目录保持干净：没有运行时目录（`.agents/`）、没有空占位目录；`src/` 里只放成套系统，不放临时文件

## 15. 已知取舍

- **放弃流程完备性**：不设 PR 评审、不设三级风险分级、不设强制需求审查 —— 换启动速度
- **放弃流程确定性**：skill 只给判断标准和选项，不规定步骤，同一个任务两次可能走不同路径 —— 换模型对具体情况的判断力
- **放弃通用性**：先只服务 Next.js/React + TS 全栈，跨技术栈复用等真有第二个项目再说
- **保留六条红线**：伪造完成、改检查、静默扩范围、破坏已有工作、带出秘密、替用户拍低可逆决策 —— 唯一不能省的成本
- **接受红线只到六条**：再往上加会让每条被稀释，且提示词本就管不住「不能有例外」的规则；撞两次以上的事故该配 hook 或 CI，不是加第七条
- **接受规则会过期**：被模型默认行为覆盖就删，不为体系完整保留
