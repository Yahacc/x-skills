# 个人 Vibe Coding 系统

两份常驻 + 三个按需。**这是源文件，不自动写入任何工具配置**——装到哪、装不装，由你决定。

| 文件 | 干什么 | 装到哪 | 行数 |
| --- | --- | --- | --- |
| `global-agents.md` | 红线 + 开工判断 + 收尾 review | 工具的用户级配置（对所有项目生效） | 33 |
| `project-agents.md` | 项目的栈、命令、证据、禁改区、坑 | 目标项目根的 `AGENTS.md` | 59 |
| `project-agents-guide.md` | 上面那份每段该怎么写 | 只读，不装 | 34 |
| `skills/slice-planning/` | 需求说不清或要拆时怎么切 | skills 目录 | 40 |
| `skills/frontend-feature/` | 页面、组件、样式、接口 | 同上 | 路由 33 + 参考 34 / 32 / 41 |
| `skills/debug/` | 报错、白屏、构建失败 | 同上 | 39 |

## 三个 skill 的共同写法

每个只讲**一个核心动作**，其余全是判据、完成标准和反例：

| skill | 核心 |
| --- | --- |
| `slice-planning` | 切成穿透每层的垂直切片 |
| `frontend-feature` | 先判断碰哪层，再读那一层的判据 |
| `debug` | 先有能红的信号，再谈原因 |

它们不是流程，是参考。模型读到判据后自己决定怎么走——写死的步骤会挡住它对具体情况的判断，而判断标准不会。

## frontend-feature 为什么是两层

`SKILL.md` 只做路由，正文在 `references/`：

| 碰到 | 读 |
| --- | --- |
| 界面、布局、样式、交互状态 | `references/ui.md` |
| 接口、server action、数据校验、返回字段 | `references/api.md` |
| 组件边界、props、复用、抽不抽、评审 | `references/component.md` |

分开写三份、各自一个 skill 也能跑，但那样会出现三个 description 抢同一次触发（“加个带接口的页面”同时命中两个），模型要么重复加载，要么漏一个。合并成一个入口后，**判断发生在里面**，只需要一次触发。

组件那一份原本拆成「设计 / 新增 / 改造 / 简化 / 评审」五个场景文件，现已合并成 `component.md` 单独一份。理由：这五个场景用的是同一条方法（定位归属 → 还原行为 → 分清所有者 → 最小改动），差别只在**输出物**——改代码、出方案、还是只评审。按起点分场景，等于把同一条方法抄五遍，改一处要同步五处。

代价是多读 33 行路由。所以 `SKILL.md` 里写死了一句：不读参考就动手，等于没用这个 skill。

## 装

1. **全局**：把 `global-agents.md` 装进用户级配置。只维护这一份，其他入口做引用，不复制内容。
2. **验证真生效**：新开一个会话问「这个项目哪三类改动要先确认」。答不上来 = 没装好，或被项目级配置盖掉。**配置不验证等于没装。**
3. **项目**：复制 `project-agents.md` 到目标项目根改名 `AGENTS.md`，占位符填完——不能留空，留空比没有更危险。
4. **技能**：把 `skills/` 下三个目录整个复制进 skills 目录（`frontend-feature` 要连同 `references/` 一起）。

## 用

开工第一句它应该报「打开了哪个开关」。没报就是没读到全局文件。

装完只做一件事：**跑一个真实的跨模块改动**，看切片卡填不填得出来。填不出来说明卡片字段设计有问题，回来改这里，不是改项目。

## 改

- **启动上下文 ≤150 行**：当前 33 + 59 = 92。
- **全局 ≤40 行**：当前 33。它对每个项目生效，加错一条所有项目一起错。
- **单个 skill 的 SKILL.md ≤40 行**：参考文件不设限，但只写一件事。
- **事实不限行**，但只写「这里和别处哪里不一样」。

删规则的标准只有一条：**删掉之后模型行为不变** → 立刻删。

设计说明与取舍理由在 `docs/vibe-coding-system.md`。
