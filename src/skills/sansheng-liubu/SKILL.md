# 三省六部 · 多 Agent 编排

制度本身就是最好的 prompt。这套东西解决的不是"分工"，是**怎么让一群人各干各的但最后不乱**——靠三件事：每个角色只有一个视角、有专门的否决环节、产物只按结构传递。

## 适用范围

- 意图模糊、需要先逼出几个差异明显的方案再收敛的决策
- 需要**对抗性审查**的场合：自己的方案看起来没问题，但缺人挑毛病
- 一人公司(OPC)式交付：从想法到 PRD/执行计划，多职能并行
- 任何"想听到不同角度而不是附和"的分析请求

不要用于：单步事实查询、纯代码修改、需要实时数据但没有的场景。这类直接做，走完流程只是把一句话的事拖成十分钟。

## 为什么这么编排

| 环节 | 只允许做什么 | 拿掉它会怎样 |
| --- | --- | --- |
| 中书令 · 起草 | 从"要不要做、怎么做才有解"出 2–3 个**根本取舍不同**的方案 | 只剩一条路线，后面全是给这条路线找理由 |
| 门下侍中 · 驳议 | 只判断能否放行，不提供"更好的做法" | 没有否决权，审查就退化成附和——模型的谄媚正是在这里最致命 |
| 尚书令 · 裁决 | 依据审议决断、拆解派单，不重开辩论 | 方案停在"各有道理"，没人承担取舍 |
| 六部 · 执行 | 只看自己那份派单，守住职责边界 | 六个角色写出六份雷同的泛泛而谈 |
| 尚书令 · 汇总 | 只整合与裁剪，不新增结论 | 汇总变成二次创作，前面的分工白做 |

两条硬规则，破一条这套就不成立：

1. **上下文隔离**：每个 Agent 拿到的只有结构化上游产物，不是完整聊天记录。共享对话会让角色互相趋同（文章作者踩的坑：9 个 opus 一起跑，多轮后质量塌）。
2. **有否决边**：门下省必须能打回，且打回理由要指出"如果成立会怎样"。只挑毛病不给后果的，是废话。

## 流程

```
旨意(task)
  └─ 中书省 起草 2–3 案
       └─ 门下省 逐案审议（放行 / 条件放行 / 打回）+ 跨方案共性问题
            ├─ 全数打回 → 中书省重拟一轮（最多 1 次）
            └─ 尚书省 裁决：主线 / 降级备选 / 砍掉 → 派单给需要的部门
                 └─ 六部 并行执行（吏/户/礼/兵/刑/工，按需派）
                      └─ 尚书省 汇总 PRD（只整合，不新增）
```

## 怎么跑

1. 读 `workflow/sansheng-liubu.mjs` 全文，**原样**作为 `workflow` 工具的 `script` 传入。不要改写里面的角色文本——那是这套制度的全部；要调就调 `args`。
2. `args`：
   - `task`（必填）：旨意原文。写得越像给下属的交代越好：目标、约束、边界、不要什么。
   - `models`（可选）：按角色覆写模型，如 `{"menxia": {"provider": "...", "model": "..."}}`。让驳议环节换个模型，能进一步减少自我认同。
   - `maxDepartments`（可选，默认 6）：派单部门上限。
   - `allowWrite`（可选，默认 false）：默认全部角色**只输出文本**，不写文件、不改仓库。只有用户明确要求"直接落地成代码/文件"时才传 `true`。
3. 跑完把返回值写成一份报告，落到 `docs/sansheng-liubu/<YYYY-MM-DD>-<slug>.md`：

```
# 旨意
## 一、中书省 · 草案
## 二、门下省 · 审议
## 三、尚书省 · 裁决与派单
## 四、六部交付
## 五、PRD
## 六、过程记录（轮次 / 降级 / 未覆盖）
```

报告只做编排，不改写内容：审议的驳回理由、派单的约束，都按原样落进去——过程可回溯才是这套东西的价值。

## 降级与失败

- `meta.degraded === true`：有环节没产出（子 Agent 失败）。**报告开头必须写明哪个环节降级**，不要把缺失的审议当成"通过了"。
- `meta.failedDepts`：哪些部门没交东西。汇总里对应章节写"未覆盖"，不许补写。
- 全数打回且重拟后仍被打回：照常裁决（尚书令有权强行定主线），但报告里要留一条"门下省两轮否决"的记录。

## 只读与开销

- 默认全部角色只输出文本。这不是洁癖：实测第一版跑下来，六部会直接往仓库里写实现文件（各写各的，还互相冲突）。编排的产物是**判断和文档**，落不落地由人决定；真要让它们动手，再传 `allowWrite: true`。
- 只读规则允许在系统临时目录里验证（造样本、跑脚本），但必须说明验的是哪个副本、跑完清理——否则"我实测过了"这句话没法核。
- 一次完整流程 6–9 个子 Agent，串行三道 + 六部并行，通常十几分钟。别拿它当单步问答用——一句话能答的事，跑完这套只会更慢更贵。

## 怎么验证改动

- 状态机逻辑不调模型也能测：`node src/skills/sansheng-liubu/workflow/sansheng-liubu.test.cjs`。用假 `agent`/`parallel` 把 `.mjs` 当函数体跑，覆盖五阶段顺序、全数打回重拟、审议/裁决失联、派单过滤与上限夹取、只读约束、schema 字段合法性。改脚本必跑，秒级。
- 改提示词后要真跑一次：小任务 + `maxDepartments: 2`，跑完 `git status` 只能有预期改动——只读约束失效的话这里会冒出新文件。
- 真跑验收看四件事：`review.verdicts` 条数等于方案数；`decision.assignments[].dept` 全在六部内；`meta.failedDepts` 与报告里"未覆盖"章节对得上；`prd` 里没有六部没给过的结论。

## 输出底线

- 方案之间必须真不一样（不同目标用户/商业模式/切法），不是同一路线的三个变体
- 驳回必须带后果，不能是"建议再打磨"
- 六部交付必须有具体数字、名字、条款、接口，禁止"需要进一步评估"
- PRD 里没有支撑的乐观表述一律删，信息不足写"未覆盖"
