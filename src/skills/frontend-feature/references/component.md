# 组件

**每一份状态、数据和逻辑都要有唯一所有者。找不到所有者证据的防御逻辑，就该删。**

新增、改造、简化、评审，都是这一条的不同起点，方法相同。

## 任何组件任务先做四步

1. **定位归属**：组件归哪个模块或包、从哪个公开入口暴露、直接调用方有谁。公开入口是契约，改它等于改对外行为。
2. **还原现有行为**：从代码读出它现在实际做什么——输入、默认值、状态、事件、副作用、生命周期。不是读它「应该」做什么。
3. **分清所有者**：业务事实 / 展示状态 / 派生值 / 副作用 / 外部契约，各归谁。派生值直接算，不留第二份可变副本。
4. **最小改动**：只改达成目标所需的文件。共享组件沿直接调用方确认影响范围，不顺带清理无关代码。

## 先确认要哪种输出

| 要的     | 做                                                        | 不做                       |
| -------- | --------------------------------------------------------- | -------------------------- |
| 改代码   | 上面四步 + 针对性验证                                     | 旁支重构、顺手升级依赖     |
| 只出方案 | 目标与边界 / 建议结构与数据流 / 关键取舍 / 待确认项       | 改文件                     |
| 只评审   | 按严重度列 findings，每条带位置、代码证据、触发条件、影响 | 改文件；把风格偏好写成缺陷 |

评审时没有证据的问题写成「问题或残余风险」，不写成确定缺陷。没发现问题就明说，并交代未验证范围。

## 需要证据才保留的东西

以下都不是无条件删除规则，删改前查实际调用和请求时序：

- **请求与竞态控制**（request id、pending 队列、重复判空）：只在并发、卸载后回写或陈旧响应可见时保留。页面每次打开都重载、且无并行覆盖时，不留跨会话协调状态。
- **初始化列表**：调用方不提供初始化数据、组件也没有真实初始化路径时，这份状态是重复的。
- **多份选中数据**：输出和 UI 都只需要完整对象时，别再单独维护一份 ID 列表；下游只消费 ID 时才按实际契约选一种。
- **抽象**：只保留能解释重要业务约束的。固定 columns、字段映射、选项集合直接写，不做可配置引擎或通用适配层。

反过来同样成立：**先证明现有复杂逻辑与目标冲突，再替换它。** 看起来冗长不等于与需求冲突——它可能正是别人依赖的契约。

## 反例

- 组件里五个 `useState` 布尔量 → 这是一个枚举，不是五个开关
- 组件里出现 fetch 或写库 → 所有权错位，IO 属于调用方或数据层
- 为「以后可能复用」扩大 props → 没有消费者就没有契约
- 新建组件时复制一个过期实现 → 先搜仓库现有模式
- 规则与代码事实冲突时静默按规则改 → 应指出冲突，再按用户决定走
