# 排查

核心只有一条：**先有一个能红的信号，再谈原因。** 没有可复现的失败信号时，读代码得出的结论都是猜测——而猜测会让你改三处、好一处、坏两处。

## 先建信号

按成本从低到高找：

1. 已有测试能不能复现
2. `curl` 打一次真实接口，看状态码与返回体
3. 直接跑那条失败的命令（`build` / `typecheck` / `dev`），读完整输出
4. 把失败路径缩成一个最小脚本或最小页面
5. 二分：上次正常的状态 vs 现在，`git bisect` 或注释掉一半

信号要满足三点：**因为这个 bug 会变红、每次结果一致、几秒内跑完**。三秒稳定的信号，比一分钟偶发复现强得多。偶发问题不求稳定复现，求**提高复现率**：循环 100 次、加压、收窄时间窗；能复现到 50% 就可排查。

## 然后才是假设

一次列出 3–5 个原因，每个都写出「如果是它，改什么会让现象消失」。说不出预测的，是感觉不是假设。一次只改一个变量——改两处后现象变了，你不知道是谁起的作用。

## 修完

- 原始场景重跑一次，确认不再出现
- 有合适接缝就补一条回归测试；**没有接缝本身就是发现**——这块改不动、测不了
- 删掉临时日志和调试代码（给日志统一前缀，收尾一次 grep 清干净）

## 反例（识别标志）

- 还没复现就开始改代码 → 最高频的浪费
- 报错只看第一行 → 真正原因常在第 3–10 行或 cause 链里
- 同时改三处「试试看」→ 结果无法归因
- 用 `try/catch`、`as any`、`@ts-ignore` 让报错消失 → 症状没了，问题还在
- 修完没重跑原场景 → 可能修的是另一个 bug
