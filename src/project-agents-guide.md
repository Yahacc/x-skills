# 项目事实怎么写

这份参考管的是「项目 `AGENTS.md` 里那几段该怎么写」，不管代码怎么写。事实属于项目，不属于任何 skill。

## 目录地图

筛选后的稳定索引，不是完整 `tree`。只列能帮忙定位的边界：源码、应用入口、共享组件、运行时、测试、构建配置。每项一句话职责，重要区域补一句改动影响。

从仓库文件核实：workspace / package 配置、根导出、路由、测试配置、现有文档。**用代码证据补足，不把猜测写进事实。** 目录频繁变化时，只保留稳定的顶层和关键入口。

## 每一段该记什么

| 段 | 记什么 | 判断问题 |
| --- | --- | --- |
| 一句话 | 产品解决什么问题、给谁用 | 说给没听过这个项目的人 |
| 栈 | 框架版本、语言、样式方案、数据层、部署目标 | 换个人接手要先知道什么 |
| 命令 | 原样可复制，不写「用你习惯的包管理器」 | 我能不能直接粘贴执行 |
| 证据 | 每类改动怎么证明（截图 / curl / 测试 / 构建） | 做完我拿什么给你看 |
| 目录地图 | 5–8 个决定改动落点的目录与职责 | 这个功能该写在哪个目录 |
| 禁改区 | 路径 + 为什么，动过会发生什么 | 哪些地方碰之前必须先问人 |
| 约定 | 命名、样式 token、请求封装、错误处理 | 这里和别处不一样在哪 |
| 状态 | 是否已上线、线上关键路径 | 这个改动会不会影响正在用的人 |
| 坑 | 现象 → 结论，一行一条 | 上次踩过什么，怎么绕开的 |

## 不该写进去的

- **某一项目里的组件经验、字段名、包名**：那是项目事实，不能变成跨项目规则
- **完整文件清单、低层实现细节**：会过期，而且没人维护第二份
- **产品愿景、迭代计划、排期**：那是你的笔记，不是 AI 干活需要的事实
- **猜想和「应该是这样」**：先查代码，查不到就问

## 维护

架构边界变了改「目录地图」与「状态」；命令变了改「命令」；踩过的坑进「坑」。文档与代码冲突时先指出来，再按你的目标更新——不要静默按旧文档执行。
